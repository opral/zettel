# Zettel v1 — candidate specification

Status: development draft, not a published stable release. This branch defines the contract and a reference validator at `@opral/zettel-ast/v1`. The existing package root, HTML package, and Lexical package still implement the [legacy 0.2 representation](legacy-0.2.md); do not feed v1 documents into those adapters.

Zettel standardizes a small Portable Text–based document vocabulary: text, annotations, and explicit containers. It is a JSON data format, independent of editors, databases, assets, and merge algorithms. MUST, MUST NOT, and SHOULD describe conformance requirements.

## Envelope and Portable Text relationship

```json
{
  "format": "zettel",
  "version": 1,
  "blocks": [
    {
      "_type": "block",
      "_key": "paragraph_1",
      "style": "normal",
      "markDefs": [],
      "children": [
        {"_type":"span","_key":"text_1","text":"Hello, world.","marks":[]}
      ]
    }
  ]
}
```

The root is an ordered block array inside a versioned envelope. An empty `blocks` array is valid. The envelope has exactly `format`, `version`, and `blocks`; application metadata belongs outside it. A body column stores the complete envelope.

Zettel retains Portable Text's `_type`, `_key`, `block`, `span`, `style`, `marks`, and block-local `markDefs`. The envelope is Zettel-specific; its `blocks` array is the Portable Text–based content. Containers and other object blocks require registered renderers in a generic Portable Text implementation. A stock renderer is not a complete Zettel implementation.

Native Portable Text `listItem`/`level` fields and `style:"blockquote"` are not canonical Zettel v1. Explicit list/item and quote containers express multiple paragraphs, nested quotes, and nested lists without inferring ownership from neighboring blocks. This is a deliberate profile choice, not a claim that Portable Text cannot express simpler lists or custom containers.

A complete [nested review example](examples/review.json) demonstrates shared annotations and a multi-paragraph list item.

## Node vocabulary

All nodes and annotation definitions MUST have `_type` and `_key`. All objects are closed: only specified fields are allowed. Types shown below are illustrative; exported TypeScript and JSON Schema describe the structure and runtime validation checks cross-node invariants.

| Type | Additional fields | Meaning |
| --- | --- | --- |
| `block` | `style`, `children`, `markDefs` | Prose paragraph or heading |
| `span` | `text`, `marks` | Nonempty run of text |
| `link` | `href`, optional `title` | A block-local link annotation definition |
| `zettel_list` | `kind`, `items`, conditional `start` | Bullet, numbered, or check list |
| `zettel_list_item` | `blocks`, conditional `checked` | One list item containing blocks |
| `zettel_quote` | `blocks` | Blockquote containing blocks |
| `code` | `code`, optional `language` | Literal block code |
| `zettel_rule` | none | Thematic break |

`span`, `link`, and `zettel_list_item` are not root blocks. `link` occurs only in `markDefs`. Inline children contain spans and explicitly registered application inline atoms; no nested prose blocks.

### Prose and annotations

`style` is `normal` or `h1` through `h6`. `children` and `markDefs` are required arrays, both possibly empty. An empty paragraph has `children:[]`; empty spans are invalid. Prose text MUST use LF for hard line breaks and MUST NOT contain CR. Importers normalize CRLF/CR at the boundary. Code strings remain literal, including their line endings.

`marks` is a required array containing decorator names and/or keys of definitions in that same block. It is semantically an unordered set, with no duplicate entries. Defined decorators are `strong`, `em`, `strike-through`, `underline`, and `code`. A span can combine decorators with at most one link annotation. Unused definitions are allowed. Links with equal URLs need not share identity.

A `link` has a nonempty `href` and optional string `title`. Its `_key` MUST NOT equal a decorator name. Rendering implementations MUST apply their own URL policy; a structurally valid string is not a promise that a URL scheme is safe to navigate.

```json
{
  "_type":"block","_key":"p","style":"normal",
  "markDefs":[{"_type":"link","_key":"link_1","href":"https://example.com"}],
  "children":[
    {"_type":"span","_key":"a","text":"Read ","marks":["link_1"]},
    {"_type":"span","_key":"b","text":"the proposal","marks":["strong","link_1"]}
  ]
}
```

Both spans refer to one logical link, so changing its destination updates one definition. Renderers SHOULD preserve this shared annotation as a single link where possible. The document does not prescribe nesting order for decorators.

### Lists and quotes

`zettel_list.kind` is `bullet`, `number`, or `check`. `items` MUST be nonempty. Each item has a nonempty `blocks` array, allowing paragraphs, nested lists, quotes, code, and registered application blocks.

Numbered lists MUST have an integer `start` between 0 and 2147483647 inclusive. Other list kinds MUST omit `start`. Every checklist item MUST have boolean `checked`; other list items MUST omit `checked`. A list item is one semantic item regardless of its number of child paragraphs. Renderers must not treat every paragraph as another item.

`zettel_quote.blocks` is ordered and may be empty. Wrapping a paragraph in a quote creates a container with a new key and retains the paragraph's key. This is a structural transformation; paragraph-to-heading is a style change retaining the same block identity.

### Code and dividers

`code.code` is a string, possibly empty. `language`, when present, is a string; adapters may reject values their destination format cannot represent. A `zettel_rule` has only `_type` and `_key`.

## Keys, editing, and merging

Every `_key` MUST be a nonempty ASCII string matching `[A-Za-z0-9_-]+`, unique across the whole document, including nested blocks, list items, spans, annotations, and extension atoms. The envelope itself has no key. Generated keys SHOULD use collision-resistant randomness. The reference implementation exposes `generateKey()`.

- Editing text, a URL, or paragraph style retains the relevant key.
- Moving a node retains its key.
- Copying a subtree creates fresh keys for every copied node/definition and remaps annotation references within it.
- Splitting retains the original key on one surviving piece and allocates fresh keys for other pieces; definitions duplicated into another block need new keys and remapped marks.
- Joining retains one surviving identity and retires the others, preserving/remapping definitions as required.

Keys are not positions, content hashes, editor-runtime keys, or database row references. Markdown import creates fresh keys; Markdown is not an identity-preserving backup format.

Stable keys enable merge implementations but do not define a CRDT or guarantee preservation of all concurrent edits. Lix can use ordinary cell LWW. A structural merger can combine supported changes, prefer the host-designated winner on overlap, validate its candidate, and return the complete winning body if the candidate is invalid or unsupported. No unresolved-conflict API is required by this format.

## Application extensions and unknown content

Applications may register explicitly named inline atoms or block atoms, such as `lix_ref` or `lix_attachment`. Names reserved by core and names beginning `zettel_` MUST NOT be overridden. Extensions define their exact payload shape; their `_key` obeys the same global identity rules. The v1 reference validator takes small `inline` and `blocks` callback maps for this purpose. Callbacks receive a detached JSON copy of the atom, so callback mutations cannot alter the input document. This draft does not define extension containers, custom annotation definitions, or an extension discovery protocol.

A strict editor MUST reject unsupported types, versions, or fields before editing. A viewer may render a placeholder, but MUST retain the original document if it stores it. Silently dropping unknown blocks, fields, or marks on save is not conformant. Read-only opaque retention does not mean that an unknown document passes a known-profile validator.

References, account IDs, asset identifiers, MIME types, bytes, notifications, permissions, and attachment upload APIs are application concerns. [The Lix demo profile](../examples/lix-comments/PROFILE.md) shows two application atoms without adding Lix concepts to Zettel core.

## Markdown interchange

Markdown is an import/export surface, not canonical storage. A converter MUST state its dialect and unsupported constructs. The demo uses CommonMark with GFM strikethrough and task lists, normalizes soft line breaks to spaces and hard breaks to LF, and supports headings, prose marks, links, lists, blockquotes, fenced code, and thematic breaks.

Unsupported or lossy cases MUST produce an explicit diagnostic in strict conversion. Examples include raw HTML, tables in this profile, underline in ordinary Markdown, empty paragraphs, and missing attachment display text. Applications may offer an explicitly lossy export separately. No byte-for-byte Markdown source roundtrip or preservation of `_key` values is promised.

Lix mention/attachment URI conventions are application-specific and documented with the demo. External images need asset ingestion before they become stored attachments. Markdown conversion cannot supply an FK guarantee for an embedded reference.

## Validation and compatibility

The core JSON Schema covers shape. Runtime validation additionally checks global key uniqueness, block-local annotation references, decorator collisions, and list-item conditions. Validation MUST NOT coerce, add defaults, strip fields, or mutate input. JavaScript callers must provide ordinary JSON data: the reference validator rejects accessors, hidden properties, sparse arrays, cyclic values, and non-JSON payloads rather than accepting data that would change on serialization. Core-only validation rejects unregistered application atoms.

A v1 document is a breaking data-format change from legacy `{type:'zettel_doc',content:[...]}` with `zettel_key` and embedded mark objects. It needs explicit conversion; changing a version field is not migration. No automatic legacy migration is shipped in this branch. Package root exports and legacy adapters remain isolated while the `/v1` candidate is reviewed.

Prior experiments demonstrated custom Tiptap/Lexical bindings for the equivalent container model. They are evidence of feasibility, not shipped v1 bindings, production editing conformance, or proof of lossless arbitrary-editor conversion. This branch's demo renders v1 directly and offers Markdown and JSON authoring.
